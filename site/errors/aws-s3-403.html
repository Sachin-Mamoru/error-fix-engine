AWS S3 403 Forbidden – Access Denied

Encountering AWS S3 403 Forbidden – Access Denied means your AWS identity lacks the necessary permissions to perform the requested operation on an S3 resource; this guide explains how to fix it by systematically checking IAM, bucket policies, and other S3 security layers.

What This Error Means

The 403 Forbidden HTTP status code indicates that the server understands the request but refuses to authorize it. In the context of AWS S3, this means your AWS identity (IAM user or role) is attempting an operation (like GetObject, PutObject, ListBucket, DeleteObject) on an S3 bucket or object, but one or more of AWS's robust security layers are preventing that action. It's not a "resource doesn't exist" error, but rather a definitive "you are not allowed to do that." This error often manifests when using the AWS CLI, SDKs, or applications interacting with S3.

Why It Happens

AWS S3 security is multifaceted, incorporating IAM policies, S3 bucket policies, Access Control Lists (ACLs), S3 Block Public Access settings, and even KMS key policies if encryption is involved. A 403 error typically arises when a request is denied by any one of these layers. It's often a permissions mismatch: either your identity lacks an explicit Allow statement, or there's an explicit Deny statement somewhere in the policy hierarchy that takes precedence. I've seen this in production when an application's service role, which once worked fine, suddenly hit a 403 after a new bucket policy was applied or an object was encrypted with a new KMS key it didn't have access to.

Common Causes

Here are the most frequent culprits behind an AWS S3 403 Forbidden error:

  • IAM User/Role Permissions: The IAM user or role making the request simply does not have the necessary permissions (e.g., s3:GetObject, s3:PutObject, s3:ListBucket) attached via its IAM policies.
  • S3 Bucket Policies: The bucket policy attached to the target S3 bucket explicitly denies access to your IAM principal, or it doesn't explicitly grant the required permission. Condition blocks within bucket policies can also deny access if their criteria aren't met (e.g., aws:SourceVpce, aws:Referer).
  • Access Control Lists (ACLs): Although S3 bucket policies are generally preferred, ACLs still apply, especially for legacy buckets or cross-account operations where objects might have specific ACLs. An object's ACL might override a bucket policy in certain scenarios, particularly concerning object ownership.
  • S3 Block Public Access Settings: These account-level and bucket-level settings are designed to prevent unintended public exposure. However, overly restrictive settings can sometimes block legitimate cross-account or even internal access that appears as a 403.
  • KMS Key Permissions: If the S3 object is encrypted using Server-Side Encryption with AWS KMS keys (SSE-KMS), the IAM principal needs specific permissions on the associated KMS key (e.g., kms:Decrypt, kms:GenerateDataKey). A missing or incorrect KMS key policy will result in a 403.
  • VPC Endpoint Policies: If your S3 access originates from within an Amazon VPC through a VPC endpoint for S3, the VPC endpoint policy itself can restrict access to specific buckets or AWS principals, leading to a 403.
  • Object Ownership: When objects are uploaded by different AWS accounts or roles, the object owner might differ from the bucket owner. This can impact permissions, especially if "Bucket owner enforced" setting isn't enabled.
  • Incorrect Region: While usually leading to other errors, attempting to access an S3 bucket in a different region without specifying the correct region in your CLI or SDK configuration can sometimes result in a 403.

Step-by-Step Fix

Troubleshooting this error requires a methodical approach. Start with the most common issues and work your way down.

  1. Identify the AWS Principal and Action:

    • Determine which IAM user or role is making the failing request. For CLI, aws sts get-caller-identity is extremely helpful.
    • Identify the exact S3 action that is failing (e.g., s3:GetObject when downloading, s3:PutObject when uploading, s3:ListBucket when listing).
    • When using the AWS CLI, add --debug to your command. The debug output often contains valuable information about the denied request, including the canonical request and the error message returned by S3.
      bash aws s3 ls s3://your-bucket-name --debug 2>&1 | less

  2. Check IAM User/Role Permissions:

    • Go to the IAM console and navigate to the user or role identified in step 1.
    • Review all attached policies (managed policies, inline policies). Look for Deny statements that might override Allow statements.
    • Ensure that the necessary S3 permissions (e.g., s3:GetObject, s3:PutObject, s3:ListBucket) are explicitly Allowed for the target bucket or objects.
    • Pro-tip: Use the IAM Policy Simulator in the AWS console. Specify the IAM principal, the S3 bucket ARN, and the specific S3 actions. This tool can simulate permissions and identify exactly which policy statement is causing the Deny.

  3. Review S3 Bucket Policies:

    • Navigate to the S3 console, select your bucket, and go to the "Permissions" tab. Click on "Bucket policy."
    • Scan the JSON policy for Deny statements that might apply to your IAM principal or the requested action. Remember that explicit Deny always takes precedence over Allow.
    • Look for Condition blocks within Allow or Deny statements. Conditions like aws:SourceIp, aws:SourceVpce, aws:RequestedRegion, or s3:x-amz-server-side-encryption can restrict access. If these conditions aren't met, access will be denied.
    • Verify that your IAM principal is explicitly allowed to perform the necessary actions.
    • You can fetch the bucket policy using the CLI:
      bash aws s3api get-bucket-policy --bucket your-bucket-name

  4. Examine S3 Access Control Lists (ACLs):

    • While bucket policies are the primary method for managing permissions, ACLs still exist and can cause issues, especially for individual objects or cross-account access.
    • On the S3 bucket's "Permissions" tab, check "Access Control List" settings.
    • For specific objects, if you suspect an ACL issue (e.g., objects uploaded from another account), you might need to check the object's ACL.
      bash aws s3api get-object-acl --bucket your-bucket-name --key path/to/your/object.txt
    • Consider enabling "Bucket owner enforced" in the S3 Object Ownership settings to disable ACLs and simplify permissions management via bucket policies.

  5. Verify S3 Block Public Access Settings:

    • Check both the account-level and bucket-level Block Public Access settings. These are found on the S3 console.
    • Even if your intention isn't public access, an overly restrictive setting (e.g., "Block new public ACLs and uploading public objects") can interfere with cross-account access if not properly configured.

  6. Check KMS Key Permissions (if applicable):

    • If your S3 objects are encrypted with SSE-KMS, navigate to the AWS KMS console.
    • Find the customer-managed key (CMK) used for encryption.
    • Go to the "Key policy" tab and ensure that your IAM principal has the necessary kms:Decrypt (and potentially kms:Encrypt, kms:GenerateDataKey) permissions for that key. Without it, you cannot access encrypted objects, even if you have full S3 permissions. I've run into this situation frequently when new services need access to existing encrypted data.

  7. Confirm VPC Endpoint Policies (if applicable):

    • If you're accessing S3 from a VPC, go to the VPC console, navigate to "Endpoints," and select your S3 endpoint.
    • Review the associated "Policy." This policy can explicitly restrict access to specific S3 buckets or principals.

  8. CLI/SDK Configuration:

    • Ensure your local AWS CLI or SDK is configured with the correct profile, region, and credentials. Use aws configure list to see your active configuration. A common mistake is assuming one profile is active when another is being used.

Code Examples

Here are some quick, copy-paste ready commands for common checks.

  • List current AWS CLI configuration:
    bash aws configure list

  • Get your current IAM identity:
    bash aws sts get-caller-identity

  • Attempt to list bucket contents with debug output (replace your-bucket-name):
    bash aws s3 ls s3://your-bucket-name --debug 2>&1 | less
    Look for SignatureDoesNotMatch or specific AccessDenied messages in the extensive debug log.

  • Retrieve the S3 bucket policy (replace your-bucket-name):
    bash aws s3api get-bucket-policy --bucket your-bucket-name

  • Retrieve an object's ACL (replace your-bucket-name and path/to/object.txt):
    bash aws s3api get-object-acl --bucket your-bucket-name --key path/to/object.txt

  • Example IAM policy snippet allowing read-only access to a specific S3 bucket:
    json { "Version": "2012-10-17", "Statement": [ { "Effect": "Allow", "Action": [ "s3:ListBucket", "s3:GetObject" ], "Resource": [ "arn:aws:s3:::your-bucket-name", "arn:aws:s3:::your-bucket-name/*" ] } ] }

Environment-Specific Notes

The 403 Forbidden error can manifest differently depending on your operational environment.

  • Cloud (AWS Console/CLI): When troubleshooting in the AWS Console, remember that your actions are typically performed under the IAM user or role you're currently logged in as. If you're running CLI commands, you might be using a different profile, environment variables, or an assumed role, leading to discrepancies. Always use aws sts get-caller-identity to confirm the active principal for CLI commands.
  • Docker/Containerized Applications (ECS, EKS): Applications running in containers often assume IAM roles via ECS Task Roles, EKS Service Accounts (IRSA), or instance profiles. Ensure that the task role or service account role associated with your container has the correct S3 permissions. It's a common oversight to grant permissions to the EC2 instance profile but forget the specific task role. Also, verify network connectivity and security group rules if using VPC endpoints for S3 access.
  • Local Development: On your local machine, the AWS CLI or SDK usually picks up credentials from ~/.aws/credentials, ~/.aws/config, or environment variables (AWS_ACCESS_KEY_ID, AWS_SECRET_ACCESS_KEY, AWS_SESSION_TOKEN). Double-check which profile is active (AWS_PROFILE environment variable) or if any environment variables are overriding your configuration files. An incorrect region in your local configuration can also sometimes lead to unexpected 403s.

Frequently Asked Questions

  • Q: Why does it work in the AWS Console but not using the CLI/SDK?

    • A: This is a classic indicator that you're operating with different credentials or IAM principals. The Console uses the IAM user/role you're actively logged in as, while your CLI or SDK might be configured with a different profile, environment variables, or an assumed role. Use aws sts get-caller-identity for both your console session (via CloudShell or SDK calls within a browser dev console) and your local CLI to compare the active principals.

  • Q: I have AdministratorAccess policy, why am I still denied?

    • A: Even with AdministratorAccess, an explicit Deny in an S3 bucket policy, a KMS key policy, or a VPC endpoint policy will always override an Allow in your IAM user policy. Also, S3 Block Public Access settings can deny access irrespective of your IAM permissions. It's often a case of "least privilege" principles conflicting with broad access.

  • Q: Can bucket encryption cause a 403?

    • A: Absolutely. If an S3 object is encrypted with SSE-KMS, and your IAM principal does not have the necessary kms:Decrypt permission on the associated KMS key, you will receive a 403 when attempting to access that object, even if you have full S3 object permissions.

  • Q: What is the most common cause of this error in your experience?

    • A: In my experience as a platform reliability engineer, the most common cause is a subtle misconfiguration within an S3 bucket policy's Condition block. Developers often apply a seemingly correct Allow policy, but overlook a Condition that isn't met (e.g., aws:SourceVpce, s3:x-amz-server-side-encryption) or an explicit Deny from a previous configuration that was forgotten. Another frequent culprit is when object ownership changes for objects copied from different accounts, where the bucket policy is sufficient but the object's specific ACL denies the operation.
